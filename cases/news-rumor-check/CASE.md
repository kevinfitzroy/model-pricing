# CASE — news-rumor-check(新闻/传闻核实)

> 套用 [`../../WORKFLOW.md`](../../WORKFLOW.md)。给一条新闻/传闻陈述,多源核实它到底成不成立。

## 1. 目标 & 输入
- **目标**:核实一条事件/传闻是否属实,**区分已证实的事实、各方说法、和未经证实的部分**。
- **输入**:一句传闻陈述,或一条新闻链接。

## 2. 被核验单元
- 一个单元 = 传闻里的**一个可核事实点**(谁、何时、何地、做了什么、数字多少)。一条传闻通常拆成多个事实点分别核。
- 精确身份(R4):逐字记录待核的事实点,不笼统核"这条传闻真不真"。

## 3. 可信来源
- **一手**:当事方官方声明、权威机构发布、原始记录/文件、多家独立一手报道。
- **二手**:聚合、转发、自媒体转述(只作线索,不作定论)。
- ⚠️ **多源独立**很关键:同一通稿被 N 家转载**不算多源印证**(同源)。

## 4. 产出结构
- `findings.json`(套通用 schema):每个事实点 `subject`=事实点原句,`kind=event`,`fields`={who,when,where,what,claimed_by},`verdict`∈{supported|refuted|misleading|unverifiable},`source_type`,`evidence_ref`,`confidence`。
- `evidence/`:各一手来源逐字摘录 + URL + 日期。
- 分析层 `analysis.md`:综合判断(传闻整体成立/部分成立/不成立/暂无定论)+ 各方说法对照 + 仍存疑处。**与逐点事实分开。**

## 5. 范围边界
- 收:可核的客观事实点。
- 不收:对动机/影响的主观解读(归入分析层,标明是推测)。

## 6. case 专属注意
- **发展中事件**:信息会变,强标 `snapshot_date`/`fetch_date`,结论写"截至某时"。
- **同源伪多源**:核来源是否真独立。
- **否定难证**:"某事没发生"往往只能 `unverifiable`,别轻易判 refuted,除非有一手否证。
- **预测/将来时**一律不判真假。

## 7. 审计补充
- reviewer 抽查:是否拿同源当多源、verdict 是否被证据支持、发展中事件的时效标注是否到位。

## 8. 触发语
- `/factcheck news <陈述或链接>`
